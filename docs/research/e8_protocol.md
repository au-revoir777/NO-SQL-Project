# E8: latency on the real stack (protocol)

Workstream A1 of the Phase 2 plan (`docs/phase2/phase2_prompt.md`, P10). Every
earlier latency number (E4 and the README) comes from the in-memory store with
an in-process queue. E8 measures the deployed path: the event generator
publishes to Redis Streams, a consumer reads it, and the detection engine
writes to and reads from Neo4j. This protocol is committed before any E8
result is computed; later changes go under "Amendments" with their reason.

## Stack and environment

- Neo4j 5.26 community and Redis 7.4 in Docker Desktop (WSL 2 backend) on the
  development laptop, in throwaway containers (`e8-neo4j`, `e8-redis`). Neo4j
  has a 1 GB heap and a 512 MB page cache, the same as `docker-compose.yml`.
  The Python process runs on the host. Host, CPU count, the Docker and image
  versions, and the other containers running are recorded in the manifest.
  Other containers share the CPU, so these numbers describe this machine, not a
  server.
- The database is wiped and the schema recreated before every run.
- Method: the tuned proposed detector exactly as in E1 and E10
  (`tuned_proposed()`), with the shipped scorer and alert threshold 0.8, on
  `Neo4jGraphStore`. The engine's batch size is 50 events (E1's setting).

## Pipeline and timestamps (wall clock, `time.perf_counter`, one process)

- **Producer:** publishes the stream's events to a fresh Redis stream with
  pipelined `XADD`. *Paced* runs publish each event at
  t0 + (simulated time since start) / speed. *Unpaced* runs publish as fast as
  Redis accepts. `published[e]` is the time the event's `XADD` pipeline returned.
- **Consumer:** reads with `XREAD COUNT c BLOCK b` and accumulates events into
  engine batches of 50, in stream order. `read[e]` is when the event was
  decoded.
- **Engine:** `process(batch)` writes the batch to Neo4j, then detects.

## Metrics (fixed before results)

- **Ingest to write** (per event): end of the batch's Neo4j write
  (process start + the engine's `ingest` timing) − `published[e]`.
- **Detect** (per batch): the engine's dirty-region + view + detector time, as
  in E4. **Batch total** = the whole `process` call.
- **Event to flag** (per ring update that confirms, alerts or early-warns):
  end of the batch's `process` − `published[last event of the batch]`. The
  event that completed the batch is the one that made the flag possible, so
  this is the time from that event entering the stack to the flag existing.
- **Consumer lag** (per batch, when it is handed to the engine): events
  published but not yet read, and `read − published` of the batch's first event.
- **Throughput:** events ÷ (end of the last `process` − first `published`).
- Percentiles p50, p95 and p99 per run, from all values of the run, with
  nearest-rank on the sorted list.

## Runs

1. **Warm-up (excluded and reported separately):** at the start of each
   session, one unpaced baseline run (seed 999). Its numbers are stored with
   `phase = warmup` and never pooled with measured runs.
2. **Shortened E1 (paced, speed 1):** E1's five scenarios × test seeds
   1001–1003, default scenario durations, `XREAD COUNT 100 BLOCK 50`.
3. **Users sweep (unpaced, after E4):** `scale_sweep` at 1,000, 5,000 and
   20,000 users (E4's size scaling of devices, cards and IPs; 20 simulated
   seconds), seeds 1001–1003. The first 10 simulated seconds are written as a
   bootstrap (as E4 does) and only the rest is measured. The in-memory figures
   for the same streams come from re-running E4's code in the same session, so
   the comparison is on the same machine and the same streams.
4. **Redis read sweep (paced, speed 1):** baseline seeds 1001–1003, with
   `XREAD COUNT` ∈ {10, 100, 500} × `BLOCK` ∈ {5, 50, 500} ms (after HYADES,
   `bora2026hyades`).

## Correctness check

For every measured run, the same events go through the in-memory engine with
the same configuration. The check passes when:
- the stream digests are equal;
- the sequence of ring updates (ring id, change, sorted members), in order, is
  identical;
- the set of flagged rings (confirmed or alerted, with their members) is
  identical.

Every mismatch is reported, not hidden.

## Reporting

- `results/e8_stack_latency/results.csv`: one row per run, with run_id,
  scenario config hash, seed, stream digest, phase, pacing, read parameters,
  the percentiles above, throughput and the correctness check;
  `per_batch.csv` holds the raw per-batch values.
- Tables are generated by `python -m fraudsim.experiments.stack_latency
  --report docs/research/e8_tables.md`. Results and limitations go in
  `docs/research/e8_results.md`, written only after the CSVs exist. No number
  appears in the docs before its CSV.

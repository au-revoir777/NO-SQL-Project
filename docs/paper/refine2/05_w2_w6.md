All methods:
- go through the same tracker (two-hit confirmation) and the same Jaccard 0.5 matching;
- get a scorer trained on their own candidates (seeds 101–110);
- are tuned on 301–303 with a budget at least the proposed method's;
- are evaluated once on 2101–2120.

GraphSAGE training:
- 879 snapshots, 322,814 user rows (3.4% positive), 40 epochs, 18.6 min on the 2-core CPU.
- It needs node-level ring-membership labels, as the proposed scorer needs ring labels.
- Validation-snapshot node ROC AUC 0.997, PR AUC 0.955 (a sanity check, not used for selection).

Not added:
- Incremental Leiden and Louvain implementations. Their aim is to match static partitions at lower cost, so static Leiden on the whole graph every batch bounds their accuracy. Their latency is not compared.
- Spade's C++ latency.
- Temporal GNNs (TGN, TGAT).

Ranked by reviewer value per effort (all now done): GraphSAGE > FRAUDAR/Spade peeling > tuned-cap rules > Leiden > tuned Louvain.

## W3. Fair-comparison protocol (paragraph for Section IV)

> **Fair comparison.** All methods process identical event streams (a paired design), emit candidate rings of 3–25 accounts, and pass them through the same tracker, which confirms a ring after two consecutive hits. Flags are matched to true rings by Jaccard overlap of at least 0.5. Each method is scored by a logistic-regression model with isotonic calibration trained on that method's own candidates (seeds 101–110, the protocol of Section III-D); for comparison with earlier versions we also report the baselines with the scorer of the proposed pipeline. Each method's structural parameter (degree cap and cycle rule for the rules; resolution for Louvain and Leiden; minimum block score for peeling; node threshold for GraphSAGE) and its alert threshold are selected jointly on validation seeds 301–303, over at least as many grid points as the proposed method received (60 to 84 against 30); grids and selections are in the repository. The evaluation seeds (2101–2120) were declared before any run and used once. Methods that recompute on the whole graph do so after every micro-batch, so none is disadvantaged by a timer, except the Louvain and rule baselines, which keep the paper's 5 s timer.

## W4. Metrics

- **Primary:** ring F1 at the validation-selected operating point, pooled (scenario-weighted, cluster bootstrap) and per scenario.
- **Threshold-free:** ring PR AUC (recorded by the harness for scored methods).
- **Operational:** TTD (median), recall by evasion strategy, detection ms per batch (p50), false rings per run.
- **Reported in the main table even when negative:** every baseline's row, and every scenario where the proposed method loses.

## W5. Decision rule and draft wording

Confirmatory comparison: the proposed method minus the strongest baseline by validation F1 (fixed before test). Holm over the paper family (R1-H1 plus this one so far).

| Outcome | Abstract sentence | Conclusion sentence |
|---|---|---|
| Superior | "Against FRAUDAR-style peeling, Leiden, Louvain, tuned rules and a GraphSAGE classifier, each with its own calibrated scorer and the same tuning budget, the pipeline reaches ring F1 [X] against [Y] for the strongest baseline ([Z]; 95% CI of the difference [a, b], fresh test seeds)." | "…outperforms the strongest of five existing methods by [Δ] F1, most on [scenarios]." |
| Matches | "…matches the strongest baseline ([Z]) within 0.05 F1 [CI] while [cost/explainability advantage, if significant]." | "…matches…; its advantage is [named, measured property], not accuracy." |
| Loses | "…[Z] reaches higher ring F1 ([Y] vs [X]); the pipeline's advantages are [streaming cost, explanations, …]." | "…a GNN trained on ring labels from the same generator outperforms…, which bounds what rule-based pipelines can claim on synthetic data." |
| Condition | "…outperforms all baselines on [scenarios] and is outperformed by [Z] on [scenarios]." | |
